# 협업과 일관성 규칙

적용 범위: B3-1과 B3-2. 아래는 팀의 작업 규칙이며 과제 원문에 새 필수 조건을 추가하지 않는다.

## 1. 작업 시작

```text
read source/plan -> inspect git -> assign file scope -> implement
                                                           |
handoff/update docs <- review results <- run relevant checks-+
```

1. 해당 과제문 → 진행계획 → 공통 개발 문서 순서로 읽는다.
2. git status와 현재 브랜치를 확인한다. 기존 변경의 소유자·목적을 파악하고 덮어쓰지 않는다.
3. 작업 시작 전에 목표, 수정할 파일, 완료 증거를 짧게 정한다.
4. 구현 브랜치는 codex/b3-1-작업명 또는 codex/b3-2-작업명으로 만든다.
5. 여러 사람이 작업하면 파일별 담당을 나눈다. 동시에 같은 파일을 수정하지 않고, 겹치면 먼저 변경 범위를 조정한다.

## 2. 기준 문서와 변경

| 항목 | 기준 |
|---|---|
| 과제 조건 | 각 과제의 과제문.md |
| 실행 순서·완료 판정 | 각 과제의 진행계획.md |
| 코드 스타일 | CODE_CONVENTIONS.md |
| 데이터 필드·단위·요약·인계 | ARCHITECTURE.md |
| 파일 위치·생성 책임 | FILE_STRUCTURE.md |
| 설계 용어 학습 자료 | [SOFTWARE_DESIGN_TERMS.md](SOFTWARE_DESIGN_TERMS.md) — 대화 답변 원문 보존 |

### 설계 문서 작성 기준

설계 결정을 기록할 때 아래 다섯 항목을 함께 작성한다. 패턴 이름만 적고 설계 완료로 표시하지 않는다.

| 순서 | 항목 | 기록할 내용 |
|---|---|---|
| 1 | 선택한 이유 | 해결할 문제, 선택한 방식과 대안·비용 |
| 2 | 책임과 인터페이스 | 구성 요소의 역할, 입력·출력·실패 계약 |
| 3 | 의존성 방향 | 어떤 모듈이 무엇을 참조하는지, 외부 기술과의 경계 |
| 4 | 실제·테스트 구현 연결 | 구현체를 어디서 생성·선택·주입하는지. 교체 대상이 없으면 해당 없음과 이유 |
| 5 | 검증 방법 | 정상·실패·경계 조건과 확인할 증거 |

```text
problem -> responsibility/contract -> dependencies -> wiring -> verification
```

위 기준은 이후 설계 작성·갱신 시 적용한다. 용어 설명의 예시를 실제 구현 완료나 모든 패턴의 채택으로 해석하지 않는다.

- 규칙·데이터 계약 변경은 이유를 문서에 먼저 남기고, 영향을 받는 두 과제의 코드·검증을 함께 갱신한다.
- 원문은 고치지 않는다. 해석·추가 설계는 계획 문서에 구분해 기록한다.
- 공동 데이터는 B3-1에서 생성하고 B3-2로 검증해 전달한다. 각자 비슷한 데이터를 따로 받아 쓰지 않는다.
- 데이터 기준 버전과 B3-2의 사용자 수정 상태를 구분한다. 초기 일치 검증 후 CRUD로 바뀐 통계를 원본 불일치로 오판하지 않는다.

## 3. 검증과 완료 표시

- 핵심 변경에는 대표 수치와 실패·경계 사례를 확인한다. 체크리스트는 실제 증거가 있을 때만 체크한다.
- 문서 변경은 내용·링크, 계산 변경은 수치·그래프, 데이터 변경은 두 과제의 인계까지 확인한다.
- 실제 자료·실제 API 결과와 테스트 대역을 구분한다. 임의 수치·가짜 캡처로 제출 증거를 채우지 않는다.
- 개인의 설명 능력은 실행 성공과 구분해 확인한다.
- 외부 계정·키가 필요하면 필요한 항목을 알리고 해당 연결을 기다린다. 그동안 독립적으로 가능한 작업은 진행한다.

## 4. 커밋과 인계

```text
one change -> evidence -> focused commit -> review -> integrate
```

- 커밋은 의미 있는 변경 단위로 만든다. 형식은 `feat(B3-1): ...`, `fix(B3-2): ...`, `docs(B3): ...`처럼 통일한다.
- 스테이징 파일 목록과 비밀 값 포함 여부를 확인한다. 다른 과제의 무관한 변경은 함께 넣지 않는다.
- 브랜치 통합 전 충돌·필수 검증을 확인하고, 푸시 후 원격 커밋을 확인한다.
- 인계 기록에는 변경 파일, 실행 명령, 확인 결과, 데이터 버전/해시, 남은 작업을 남긴다.
- 핵심 결과와 인계 기록은 README에 누적하고 불필요한 임시 보고서를 늘리지 않는다.
