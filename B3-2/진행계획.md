# B3-2 과제 정리 및 진행 계획

갱신: 2026-10-19

기준: [과제문.md](과제문.md)의 1~8절. 원문은 별도로 보존하며, 이 문서는 원문의 필수·선택·예시를 구분한 구현 계획이다. 현재 완료 범위는 원문 문서화·계획 수립과 B3-1 정제본 인계다. 시드 CSV 1,095행과 manifest의 바이트 일치를 확인했다. 앱 구현·DB 적재·실제 AI 호출·배포·실행 증빙은 아직 수행하지 않았다.

## 1. 과제의 목표와 최종 결과

**저장된 시계열 데이터를 요약하고, 그 요약을 근거로 대화하는 웹 AI 비서**를 만든다. 사용자가 데이터를 수정하면 요약과 이후 AI 답변에도 그 변경이 반영되어야 한다.

원문 2절의 최종 결과는 아래 4가지다.

| 결과 | 사용자의 동작 | 확인할 결과 |
|---|---|---|
| 데이터 기반 AI 채팅 | 질문 입력 | 로딩 후 저장 데이터의 요약을 반영한 답변 표시 |
| 데이터 관리(CRUD) | date·mode·value·memo 추가/수정/삭제 | 목록·저장 결과 갱신 |
| 대화 기록 | 대화 저장·목록 조회·불러오기 | 저장된 대화의 전체 메시지가 다시 표시됨 |
| 배포·문서화 | 공개 URL·Swagger·README 접근 | 프론트·백엔드 접속 및 실행·환경 변수 설정 방법 확인 |

원문 3절의 학습 목표는 다음과 같이 확인한다.

| 학습 목표 | 구현에서 연결할 부분 | 설명해야 할 내용 |
|---|---|---|
| 시계열 분석과 서비스 연결 | 데이터 요약 서비스 | 원본에서 기간·개수·통계·추세를 계산하는 과정 |
| FastAPI 구조 분리 | 라우터·서비스·저장소 | HTTP 처리, 업무 계산, DB 접근을 나눈 이유 |
| Pydantic 검증 | 요청·응답 스키마 | 날짜·수치·메시지 검증의 기준과 실패 응답 |

산출물 검증과 학습자의 설명 능력은 따로 확인한다. 앱이 실행된다는 사실만으로 개인 학습 목표까지 완료 처리하지 않는다.

## 3. 기술 구성과 B3-1 연계

### 고정 기술 조건

- 백엔드: FastAPI, Python 3.10 이상.
- DB: Firebase Firestore.
- AI: OpenAI GPT API.
- 프론트: HTML/CSS/JavaScript. 프론트 프레임워크 사용 금지.
- 백엔드 배포: Render.
- 프론트 배포: Vercel.

### 주제: 같은 교통 데이터로 만드는 AI 비서

사용자의 요청에 따라 B3-1을 먼저 완성하고, **2025년 따릉이 대여·서울버스 승차·공개 지하철 승차 일별 정제본 전체**를 B3-2의 초기 자료로 사용한다. 365일×3수단=1,095행을 초기 계약으로 삼는다. B3-1에서 공식 자료 수집·분석·검증을 완료했으며, 이 과제의 DB·AI·앱은 아직 구현하지 않았다.

- 기준 파일: B3-1/data/processed/observations.csv와 manifest.json.
- 전달 위치: B3-2/data/seed/. 같은 파일을 그대로 복사하고 해시·행별 값·기간·건수를 확인한다.
- 데이터 형식: date=이용일, mode=bike/bus/subway, value=대여·승차 건수, memo=관측·수정 관련 메모. 단위는 건이다. 기본 키는 (date, mode)다.
- 질문 예: “따릉이는 주말에 얼마나 달라?”, “세 수단 중 월별 변동이 큰 것은?”, “세 수단이 함께 줄어든 날짜는?”
- 자료 밖의 질문에는 해당 기간의 자료가 없음을 설명한다. 임의의 관측값을 만들지 않는다.
- 서울시 공개자료의 범위에는 서울 밖 지하철역·버스 정류장이 포함될 수 있다. 요일·월별 이용 변화는 관찰이며 환승·대체·인과 효과로 단정하지 않는다.
- 최초 적재 결과는 B3-1과 같아야 한다. 이후 사용자 CRUD는 Firestore만 변경하고 B3-1 분석 자료·리포트는 보존한다.

공통 기준은 [코드 컨벤션](../B3-1/docs/CODE_CONVENTIONS.md), [아키텍처·데이터 계약](../B3-1/docs/ARCHITECTURE.md), [파일 구조](../B3-1/docs/FILE_STRUCTURE.md), [협업 규칙](../B3-1/docs/COLLABORATION.md)에 둔다. 이는 사용자 요청에 따른 연계 설계이며 원문의 추가 필수 조건은 아니다.

### 요청 흐름

```text
B3-1 processed CSV + manifest
             |
       copy + verify
             v
B3-2 seed -> import -> Firestore data
                           |
Browser -> FastAPI -> current summary -> system prompt -> GPT
   ^           |                                         |
   |           +<------------- answer -------------------+
   |           |
   +-- result  +--> Firestore conversations
```

GET /api/data/summary와 POST /api/chat은 같은 요약 서비스를 사용한다. 채팅마다 현재 DB에서 요약을 다시 얻어 CRUD 변경이 반영되게 한다. 서버 내부에서는 같은 서비스를 호출하며, 불필요하게 자기 서버에 HTTP 요청을 보내는 구조는 피한다.

## 4. API·저장 구조 계획

### API 10개

목록·summary는 mode와 기간 필터를 지원한다. 채팅 요청도 선택한 mode/기간을 서버에서 검증하고, 전체 비교 질문에는 수단별 요약을 제공한다. 미래 구현의 API/서비스 계약은 공통 설계의 다섯 단계로 기록한다.

| 메서드·경로 | 역할 | 주요 입력·출력 |
|---|---|---|
| POST /api/data | 데이터 추가 | date, mode, value, memo → 저장된 id와 데이터 |
| GET /api/data | 데이터 목록 | 날짜순 데이터 목록 |
| PUT /api/data/{id} | 데이터 수정 | 검증된 필드 → 수정 결과 |
| DELETE /api/data/{id} | 데이터 삭제 | 삭제 성공, 없는 id는 명확한 실패 응답 |
| GET /api/data/summary | 요약 조회 | period, count, metrics, trend와 답변에 필요한 근거 |
| POST /api/conversations | 대화 저장 | 검증된 messages·제목 → conversation_id |
| GET /api/conversations | 대화 목록 | id, 제목, 생성/수정 시각 등 메타데이터 |
| GET /api/conversations/{id} | 대화 불러오기 — A안 | 전체 messages |
| DELETE /api/conversations/{id} | 대화 삭제 | 삭제 결과 |
| POST /api/chat | AI 대화·자동 저장 | 질문, 선택적 conversation_id → 답변, conversation_id, 저장 결과 |

수동 대화 저장 API와 채팅의 자동 저장은 모두 구현한다. 기존 대화를 불러와 이어서 질문하면 동일 conversation_id의 메시지가 갱신되게 한다.

### Firestore

| 컬렉션 | 문서 필드 초안 | 확인 사항 |
|---|---|---|
| data | date, mode, value, memo, created_at, updated_at | 날짜·수단 enum·0 이상의 정수·메모 길이 검증. 날짜·수단 키의 유일성 유지 |
| conversations | title, messages, created_at, updated_at | messages의 role·content·순서 유지. 클라이언트가 시스템 프롬프트를 덮어쓰지 못하게 검증 |

날짜는 YYYY-MM-DD, 서버 기록 시각은 UTC로 통일한다. 하루 수단별 한 관측값을 유지하고 시드 문서 ID는 dataset_id·mode·date로 정한다. 재적재 시 같은 값은 건너뛰고 사용자 수정과의 충돌은 알린다. 대화 길이 상한을 정하고 초과 시 새 대화를 안내한다.

## 5. 원문 결과 예시를 적용하는 방식

원문 8절은 “정답이 아니라 참고 예시”이며 문구·디자인을 바꿀 수 있다고 명시한다. [과제문.md](과제문.md)에는 원문 예시 3개를 수정 없이 보존한다. 구현에서는 예시의 역할과 흐름을 실제 데이터에 맞게 재현한다.

| 원문 예시 | 구현에서 준수할 부분 | 검증 방법 |
|---|---|---|
| 데이터 요약 JSON | period, count, metrics, trend 구조로 현재 저장 데이터의 요약 반환 | DB를 별도 계산한 결과와 API의 기간·건수·통계·추세 비교 |
| 시스템 프롬프트 | 기간·레코드 수·지표·트렌드를 넣어 데이터 기반 답변 요청 | 테스트에서 실제 주입된 요약을 확인하고, 실제 호출에서는 답변 수치를 대조 |
| AI 대화 | 시점 비교·최고 기록 등 질문에 저장 데이터의 수치·날짜로 답변 | 정답을 계산할 수 있는 질문을 보내 API 요약·DB·화면 답변 비교 |

### 예시 숫자와 계산 정의

원문 예시의 count=180, total=32000000, average=5330000은 동일한 관측 단위에서 total/count로 계산한 평균과 일치하지 않는다. 관측 단위나 집계 기준도 예시만으로는 확정할 수 없다. 원문 숫자는 그대로 보존하되 실제 앱에서는 다음과 같이 계산 기준을 명시한다.

- count: 선택한 수단·기간의 유효 레코드 수. 전체 1,095행과 수단별 365행을 구분한다.
- period: 해당 레코드의 최소 날짜부터 최대 날짜.
- metrics.average/max/min: 같은 대상 레코드의 value로 계산.
- metrics.total: 선택한 수단의 기간 합계. 세 수단 합계를 고유 이용자 수나 수송분담률로 표현하지 않는다. 단위는 대여·승차 건수다.
- trend: 비교 구간·계산법·기준을 공개한다. 수단별 건수 차이·증감률을 사용하고 기준값이 0이면 비율은 null로 둔다.
- 요일별 평균, 월별 일평균, 최고 기록 날짜 등에 답하려면 수단별 집계와 극값 날짜를 요약에 포함한다. 근거가 없으면 값을 만들어 답하지 않는다.

최근 추세는 “선택 수단의 마지막 관측일 기준 최근 7일 평균과 그 이전 7일 평균의 차이”다. 날짜 누락과 각 구간의 유효 개수를 검사하고, 비교 자료가 부족하면 “판단 불가”로 표시한다. 증가/감소/유지의 허용 오차는 데이터 정밀도를 확인한 뒤 정하고 문서화한다.

빈 데이터에서는 count=0, 통계·기간은 null 등 일관된 계약으로 반환하고 데이터 부족을 안내한다. 평균을 0으로 꾸며 정상 통계처럼 표시하지 않는다.

## 6. 화면·배포·환경 변수 계획

### 화면 구성

| 화면 | 필수 구성 | 결과 확인 |
|---|---|---|
| 채팅 + 데이터 요약 | 기간·건수·지표·추세, 질문 입력, 메시지, 로딩·오류 | 같은 화면에서 요약과 질문·답변이 보이게 구성 |
| 데이터 관리 | 추가 폼, 목록, 수정·삭제 | 조작 후 저장된 목록과 요약 갱신 |
| 대화 기록 | 목록, 선택·불러오기, 대화 삭제 | 새로고침 후에도 저장된 전체 대화 복원 |

일반적인 실패는 빈 입력·잘못된 날짜/값·없는 문서·AI 인증/한도/지연·DB 저장 실패로 나누어 안내한다. 실패 후 입력을 유지하고 다시 시도할 수 있게 한다. AI 응답은 받았지만 대화 저장에 실패했다면 저장 완료로 표시하지 않는다.

### 환경 변수

| 이름 | 위치 | 용도 |
|---|---|---|
| OPENAI_API_KEY | 로컬 백엔드·Render | GPT API 인증. 서버에서만 사용 |
| FIREBASE_SERVICE_ACCOUNT_JSON | 로컬 백엔드·Render | 서비스 계정 JSON. 원문이 허용한 키 파일 경로 방식으로 대체 가능 |
| ALLOWED_ORIGINS | 로컬 백엔드·Render | 실제 프론트 주소와 로컬 개발 주소의 CORS 허용 목록 |
| API_BASE_URL | 로컬 프론트 빌드·Vercel | FastAPI 주소. 브라우저에서 사용되는 공개 설정 |
| OPENAI_MODEL | 백엔드, 추가 설계 | 구현 시 계정에서 사용 가능한 GPT 모델 선택 |
| MAX_OUTPUT_TOKENS | 백엔드, 추가 설계 | 선택한 모델·호출 방식에 맞춘 출력 토큰 상한 |

실제 비밀 값은 .env 또는 배포 환경 변수에 설정한다. Git에는 값이 없는 .env.example과 설정 방법을 남긴다. 서비스 계정 키 파일을 사용한다면 해당 파일도 Git 제외 대상으로 명시한다.

### 정적 프론트의 API 주소 주입

바닐라 JavaScript는 서버의 환경 변수를 직접 읽을 수 없으므로, 빌드 스크립트가 API_BASE_URL을 읽고 배포용 config.js를 생성하도록 계획한다. 이 파일에는 공개 백엔드 주소만 들어간다. OpenAI 키와 Firebase 서비스 계정은 프론트 산출물에 포함하지 않는다.

Vercel의 빌드 환경 변수와 정적 산출물 배포 방식을 기준으로 설계한다. [Vercel 환경 변수](https://vercel.com/docs/environment-variables), [Vercel 빌드](https://vercel.com/docs/builds).

### 배포 설정 초안

- Render Root Directory: B3-2/backend. 설치는 requirements.txt 기준, 시작 명령은 `uvicorn main:app --host 0.0.0.0 --port $PORT`로 구성한다. [Render FastAPI 배포](https://render.com/docs/deploy-fastapi).
- Vercel Root Directory: B3-2/frontend. 정적 빌드 스크립트로 dist를 생성해 배포한다.
- Render API 주소를 Vercel의 API_BASE_URL에, Vercel 주소를 Render의 ALLOWED_ORIGINS에 설정한다.
- Render 무료 웹 서비스는 비활성 상태 후 중지될 수 있으므로 처음 접속할 때 서버 준비 안내를 제공한다. 대기 중 자동으로 AI 요청을 반복하지 않는다. [Render 무료 서비스](https://render.com/docs/free).
- Firebase 인증은 서버 환경에서 구성한다. JSON 내용 또는 환경 변수가 가리키는 키 파일을 사용하고, 브라우저에 관리 권한 키를 전달하지 않는다. [Firebase Admin SDK 설정](https://firebase.google.com/docs/admin/setup).

계정 연결이나 서비스 생성은 이 계획 단계에서 수행하지 않았다. 구현 시 연결이 필요한 단계까지 준비하고, 사용할 계정·키가 없으면 해당 연동 작업은 입력을 기다린다. 키를 채팅이나 문서 본문에 적도록 요청하지 않는다.

## 10. 보너스 범위

필수 서비스와 제출 증빙을 먼저 완성한다. 보너스는 별도 선택 시 수행한다.

| 선택 항목 | 원문의 구성 요건 |
|---|---|
| 도구 호출 + 멀티채널 | Function Calling 도구 스키마·연결, MCP Server 또는 GPT Actions 중 1개 연동, README에 도구 선택 근거·호출 흐름 |
| 인사이트·UX 고도화 | 추가 지표 1개 이상, 프론트 그래프 1개, CSV 또는 JSON 내보내기, 다크 모드 토글 |

기본 컨텍스트 주입만 구현한 상태를 Function Calling·MCP 완료로 표현하지 않는다. 일부 기능만 추가한 경우에도 보너스 전체를 완료했다고 표시하지 않는다.
