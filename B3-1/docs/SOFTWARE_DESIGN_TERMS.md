맞습니다. **앞서 작성한 문서는 작업 규칙과 파일 배치 중심이었고, 실제 코드를 어떤 설계 방식으로 구성할지는 충분히 정하지 않았습니다.** 모듈을 분리한다고만 했지, 객체를 사용할지, 의존성을 어떻게 연결할지, 인터페이스와 구현체를 어디서 나눌지까지 설명하지 않았습니다.

그리고 **“한 함수는 한 책임을 가진다”는 함수형 프로그래밍을 선택했다는 뜻이 아닙니다.** 절차형·객체지향·함수형 어디에서든 적용할 수 있는 설계 원칙입니다.

말씀하신 내용을 포괄하는 대표 분야는 **소프트웨어 설계(Software Design)**입니다. 그 안에서 다음 구분을 잡으면 용어들이 정리됩니다.

```text
Software Design
|
+-- Paradigm             코드를 어떤 사고방식으로 구성하는가
+-- Design Principles    좋은 설계를 판단하는 기준은 무엇인가
+-- Architecture         시스템의 책임과 의존성을 어떻게 나누는가
+-- Design Patterns      반복되는 설계 문제를 어떻게 해결하는가
+-- Contracts           구성 요소 사이에 어떤 약속을 두는가
+-- Implementation      함수·객체·모듈로 어떻게 구현하는가
`-- Verification        설계와 동작을 어떻게 검증하는가
```

이 분류들은 서로 연결되며, 하나만 선택하는 관계가 아닙니다.

**1. 프로그래밍 패러다임: 코드를 구성하는 사고방식**

| 용어 | 핵심 의미 | 우리 과제에 적용하면 |
|---|---|---|
| **절차형 프로그래밍 — Procedural Programming** | 작업을 수행하는 절차와 함수 중심으로 구성 | 자료 읽기 → 정제 → 분석 → 그래프 저장 |
| **객체지향 프로그래밍 — OOP** | 상태와 관련 동작을 객체로 묶고 객체들이 협력하게 구성 | DB 접근을 담당하는 저장소 객체, AI 호출을 담당하는 클라이언트 객체 |
| **함수형 프로그래밍 — FP** | 값의 변환, 순수 함수, 불변성을 중심으로 구성 | 같은 관측값을 입력하면 같은 통계를 반환하는 계산 함수 |
| **선언형 프로그래밍 — Declarative Programming** | 수행 절차보다 원하는 결과를 표현 | SQL 집계, DataFrame의 그룹별 집계 표현 |

실제로는 혼합할 수 있습니다. B3-1은 절차적인 실행 흐름 안에서 계산을 순수 함수로 작성하고, B3-2는 외부 연결을 객체로 감싸는 식입니다.

**함수를 많이 사용한다고 함수형은 아니며, 클래스를 사용한다고 객체지향 설계가 잘된 것도 아닙니다.**

**2. 함수·객체·인터페이스: 코드를 구성하는 기본 단위**

| 용어 | 의미 | 예시 |
|---|---|---|
| **함수 — Function** | 입력을 받아 특정 작업을 수행하는 단위 | `calculate_summary(records)` |
| **메서드 — Method** | 클래스나 객체에 속한 함수 | `repository.list_records()` |
| **클래스 — Class** | 객체의 데이터와 동작을 정의하는 틀 | `FirestoreObservationRepository` |
| **객체 — Object** | 실행 중 존재하며 상태나 동작을 제공하는 값 | 설정된 Firestore 연결을 사용하는 저장소 인스턴스 |
| **모듈 — Module** | 관련 코드를 묶은 단위 | Python의 `metrics.py` |
| **캡슐화 — Encapsulation** | 내부 상태와 구현을 정해진 경계를 통해 다룸 | 호출자는 저장소 메서드를 사용하고 DB 세부 코드를 직접 다루지 않음 |
| **추상화 — Abstraction** | 사용에 필요한 핵심만 드러내고 세부 구현을 감춤 | “관측값을 조회한다”는 기능만 노출 |
| **인터페이스 — Interface** | 다른 구성 요소가 사용할 수 있는 기능과 약속 | `list_records()`가 어떤 값을 반환하고 어떤 실패를 알리는지 |
| **구현체 — Implementation** | 인터페이스의 약속을 실제로 수행하는 코드 | Firestore 구현체, 메모리 구현체 |
| **합성 — Composition** | 다른 객체를 포함하고 사용해 기능을 구성 | 채팅 서비스가 저장소와 AI 클라이언트를 전달받아 사용 |
| **상속 — Inheritance** | 기존 클래스의 정의를 확장하거나 특수화 | 공통 기반 클래스를 상속한 구현체 |

인터페이스는 반드시 별도 파일이나 `Interface`라는 이름의 클래스를 뜻하지 않습니다. Python에서는 메서드 사용 규칙, `Protocol`, 추상 기반 클래스 등으로 표현할 수 있습니다.

**3. 설계 원칙: 왜 그렇게 나누는지 판단하는 기준**

| 용어 | 핵심 의미 | 적용 예 |
|---|---|---|
| **관심사 분리 — Separation of Concerns** | 서로 다른 종류의 문제를 분리 | HTTP 처리, 통계 계산, DB 접근을 분리 |
| **단일 책임 원칙 — SRP** | 하나의 구성 요소가 서로 무관한 이유로 변경되지 않게 함 | DB 변경 때문에 통계 계산 코드까지 고치지 않음 |
| **응집도 — Cohesion** | 한 구성 요소 내부의 책임들이 얼마나 밀접한가 | 통계 계산 함수들을 분석 모듈에 모음 |
| **결합도 — Coupling** | 다른 구성 요소의 세부 사항에 얼마나 의존하는가 | 분석 함수가 Firestore 응답 형식을 직접 알면 결합도가 높음 |
| **의존성 역전 — DIP** | 핵심 정책이 외부 기술의 세부 구현에 직접 종속되지 않게 함 | 채팅 로직이 구체적인 Firestore 클래스 대신 저장소 계약에 의존 |
| **개방·폐쇄 원칙 — OCP** | 예상되는 확장은 기존 핵심 코드의 변경을 줄이며 수용 | 저장소 구현체를 교체해도 요약 로직 유지 |
| **DRY** | 같은 지식이나 규칙의 중복을 줄임 | 평균 계산 규칙을 API와 채팅에서 각각 다르게 구현하지 않음 |
| **KISS** | 필요한 문제를 단순한 설계로 해결 | 작은 분석 프로그램에 불필요한 계층을 추가하지 않음 |
| **YAGNI** | 아직 필요하지 않은 기능과 추상화를 미리 만들지 않음 | 사용할 계획이 없는 여러 DB 지원을 먼저 구현하지 않음 |

엄밀히 말하면 SRP를 단순히 “함수는 한 가지 일만 한다”로 설명하는 것은 축약입니다. 핵심은 **책임과 변경 이유의 일관성**입니다.

```text
generate_report()
    |
    +-- read_data()
    +-- calculate_statistics()
    `-- render_report()
```

`generate_report()`는 여러 함수를 호출하지만, **리포트 생성 절차를 조정한다는 하나의 책임**을 가질 수 있습니다. 함수가 한 줄이거나 동작이 하나여야 하는 것은 아닙니다.

**4. 아키텍처와 업무 로직: 시스템의 어느 부분을 맡는가**

| 용어 | 핵심 의미 | B3 적용 예 |
|---|---|---|
| **도메인 — Domain** | 프로그램이 다루는 문제 영역 | 기온 관측, 시계열 분석, 데이터 기반 질의 |
| **비즈니스 로직 / 도메인 로직** | 해당 문제 영역의 규칙과 판단 | 평균 계산, 유효 관측값 기준, 최근 두 구간 비교 |
| **애플리케이션 로직 — Application Logic** | 사용자 목적을 수행하도록 작업을 조정 | 데이터 조회 → 요약 → AI 요청 → 대화 저장 |
| **유스케이스 — Use Case** | 사용자가 달성하려는 하나의 목적 | “현재 자료를 근거로 질문하고 답변받기” |
| **인프라스트럭처 — Infrastructure** | DB·파일·네트워크 등 외부 기술 구현 | Firestore SDK, OpenAI 호출, CSV 읽기 |
| **표현 계층 — Presentation Layer** | 사용자나 외부 요청과 결과를 주고받는 경계 | 웹 화면, FastAPI 라우터 |
| **계층형 아키텍처 — Layered Architecture** | 역할별 계층으로 시스템을 구분 | Router → Service → Repository |
| **포트와 어댑터 — Ports and Adapters** | 핵심 로직과 외부 기술을 계약으로 분리 | 저장소 포트에 Firestore 어댑터 연결 |
| **클린 아키텍처 — Clean Architecture** | 핵심 규칙이 외부 프레임워크·DB에 의존하지 않도록 구성 | 업무 규칙에서 FastAPI·Firestore를 직접 참조하지 않음 |
| **데이터 파이프라인 — Data Pipeline** | 데이터를 단계별로 변환하는 구조 | 원본 → 정제 → 집계 → 시각화 |
| **Functional Core, Imperative Shell** | 계산은 순수 함수로, 입출력과 실행 순서는 바깥에서 처리 | 통계 함수와 파일 읽기·저장 코드를 분리 |

여기서 **비즈니스 로직은 상업적인 기능만 뜻하지 않습니다.** 우리 과제에서는 “어떤 자료를 유효한 관측값으로 보고 어떻게 분석하는가”가 업무 규칙입니다.

또한 `Service`라는 이름의 파일을 만들었다고 업무 로직이 잘 분리되는 것은 아닙니다. 그 안에 HTTP·DB·계산 코드가 모두 섞여 있으면 책임 분리가 부족합니다.

**5. 설계 패턴: 반복되는 문제를 해결하는 방법**

| 용어 | 해결하려는 문제 | 적용 예 |
|---|---|---|
| **어댑터 — Adapter** | 서로 다른 인터페이스나 데이터 형식을 연결 | Firestore 문서를 프로그램의 관측값 형식으로 변환 |
| **리포지토리 — Repository** | 저장 기술의 세부 사항을 감추고 데이터를 다룸 | 관측값 추가·조회·수정·삭제 제공 |
| **전략 — Strategy** | 같은 목적의 처리 방법을 교체 | 비교 지표 계산 방식을 선택해서 실행 |
| **팩토리 — Factory** | 객체 생성과 선택을 한곳에서 담당 | 설정에 따라 실제 저장소 또는 테스트 저장소 생성 |
| **파사드 — Facade** | 복잡한 하위 작업을 단순한 진입점으로 제공 | 호출자는 `answer_question()`만 사용 |
| **의존성 주입 — Dependency Injection, DI** | 사용할 구성 요소를 내부에서 고정 생성하지 않고 외부에서 전달 | 서비스 생성 시 저장소와 AI 클라이언트 전달 |
| **컴포지션 루트 — Composition Root** | 실제 구현체를 선택하고 연결하는 시작 지점 | 앱 시작 시 설정을 읽어 서비스와 저장소 구성 |

어댑터와 리포지토리는 배타적인 분류가 아닙니다. **Firestore 리포지토리는 저장소 역할을 하면서 외부 DB를 연결하는 어댑터이기도 할 수 있습니다.**

DI와 DIP도 다릅니다.

- **DI:** 의존 객체를 전달하는 구현 기법.
- **DIP:** 핵심 로직이 무엇에 의존해야 하는지에 관한 설계 원칙.

객체를 외부에서 전달받더라도 특정 DB의 세부 형식에 종속돼 있다면 DIP를 충분히 지킨 것은 아닙니다.

**6. 계약·상태·검증: 연결이 올바른지 판단하는 용어**

| 용어 | 핵심 의미 | 적용 예 |
|---|---|---|
| **계약 — Contract** | 입력·출력·실패·행동에 관한 약속 | 없는 ID를 조회했을 때 어떤 결과를 주는가 |
| **스키마 — Schema** | 데이터의 필드·타입·구조 | `date`, `value`, `memo` |
| **DTO — Data Transfer Object** | 경계를 넘어 데이터를 전달하는 객체 | API 요청·응답용 Pydantic 모델 |
| **불변 조건 — Invariant** | 항상 유지해야 하는 규칙 | 같은 날짜의 관측값은 하나여야 함 |
| **순수 함수 — Pure Function** | 같은 입력에 같은 결과를 내고 외부 상태를 바꾸지 않음 | 관측값 목록의 평균 계산 |
| **부수 효과 — Side Effect** | 반환값 외에 외부 상태와 상호작용 | 파일 쓰기, DB 변경, 네트워크 요청 |
| **불변성 — Immutability** | 생성한 값을 직접 변경하지 않는 성질 | 원본 자료를 수정하지 않고 정제 결과를 새로 생성 |
| **멱등성 — Idempotency** | 같은 작업을 반복해도 효과가 중복되지 않음 | 시드를 다시 적재해도 관측값이 늘어나지 않음 |
| **테스트 대역 — Test Double** | 테스트에서 실제 의존성을 대신하는 구성 요소 | 외부 연결 없는 테스트용 저장소 |
| **Fake / Stub / Mock** | 간이 구현 / 정해진 응답 제공 / 상호작용 검증 중심의 대역 | 메모리 DB / 고정 AI 응답 / 호출 여부 검사 |
| **단위·통합·E2E 테스트** | 함수·구성 요소 연결·사용자 전체 흐름을 각각 검증 | 평균 계산 / 실제 DB 저장 / 브라우저 질문과 답변 |

우리가 흔히 “mock으로 실행한다”고 부르는 것도 정확하게는 **메모리 저장소는 Fake, 고정 AI 응답은 Stub**일 수 있습니다.

우리 프로젝트에 지금 필요한 설계 선택은 다음과 같습니다. **이 표는 앞선 문서에서 충분히 정하지 않았던 부분에 대한 제안입니다.**

| 대상 | 적합한 설계 | 이유 |
|---|---|---|
| **B3-1 분석 프로그램** | 데이터 파이프라인 + 순수 계산 함수 + 입출력 분리 | 분석 단계가 명확하고 수치 재현·검증이 쉬움 |
| **B3-1 코드 구성** | 함수·모듈 중심, 필요한 데이터 모델만 사용 | 상태를 가진 서비스 객체가 많이 필요하지 않음 |
| **B3-2 웹 서비스** | Router / Service / Repository 계층 | HTTP·업무 처리·DB 접근의 변경 이유가 다름 |
| **B3-2 외부 연결** | 저장소·AI 인터페이스 + 실제 어댑터 + DI | 실제 구현과 테스트 대역을 교체하기 쉬움 |
| **두 과제 연결** | 명시적인 데이터 계약 + 버전·해시 검증 | 같은 자료를 사용한다는 사실을 확인할 수 있음 |

```text
B3-1
CLI -> read -> clean -> calculate -> write
                        |
                   pure functions


B3-2
Router -> Use Case / Service
                |
                +-- Repository interface
                |       +-- Firestore implementation
                |       `-- In-memory fake
                |
                `-- AI interface
                        +-- OpenAI adapter
                        `-- Fixed-response stub
```
